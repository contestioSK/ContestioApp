Tá “oprava” s EMPTY_* konštantami je legit a rieši konkrétny React loop. Ale je tam jedna vec, ktorú si (alebo Replit) mieša:

React render loop ti zhodí UI a v konzole uvidíš Maximum update depth exceeded.

Server, ktorý “padá ticho” je iná liga: OOM kill, unhandled promise rejection, crash v scheduleri/queue, alebo nekonečný loop na Node strane.

Takže: áno, fix na [] je dobrý, ale nevysvetľuje tichý pád servera, ak sa naozaj deje.

Nižšie máš dve veci:

správny fix na ten React loop (plus robustnejšia verzia)

ako nájsť a opraviť “tichý” server crash (najčastejšie príčiny v tvojom projekte: photo pipeline / schedulery / background jobs / WS)

1) React loop – pevný fix (UI)
Najrýchlejší fix (to čo spravil Replit) ✅

Na module-level:

const EMPTY_MANUFACTURERS: ManufacturerWithFlavors[] = [];
const EMPTY_USER_BRANDS: UserBrandWithFlavors[] = [];

V komponente:

const { data: manufacturers = EMPTY_MANUFACTURERS } = useQuery(...);
const { data: userBrands = EMPTY_USER_BRANDS } = useQuery(...);
Robustnejší fix (odporúčam) ✅

Aj keby si nemal [], loop často vzniká tým, že máš useEffect ktorý robí setState a v dependency má objekt/array, ktorý sa často mení (aj keď obsah je rovnaký).

Preto v deps radšej používaj:

manufacturers.length

alebo stabilný “key” string z idčiek

Príklad:

const manufacturersKey = useMemo(
  () => manufacturers.map(m => m.id).join(","),
  [manufacturers]
);

// a potom:
useEffect(() => {
  // ... setState logika
}, [editingCatch?.id, manufacturersKey]);

Tým odstrihneš “referenčné zmeny” a effect sa nespustí pri každom renderi.

2) Server “padá ticho” – toto je reálny problém

Ak server padá bez stacktrace, 80% prípadov je:

A) OOM kill (pamäť)

Typicky: Sharp / HEIC decode / paralelné spracovanie / veľa fotiek naraz.

Symptóm: proces zmizne bez chyby v logu, len sa reštartuje.

Fixy s najvyšším ROI:

limituj paralelizmus pri spracovaní (aj keď máš queue, môžeš mať paralelné varianty)

zníž max rozlíšenie + kvalitu pri sanitize

urob hard limit na počet fotiek aj v competition uploadoch

nepoužívaj Promise.all na veľa variantov, daj p-limit(2) alebo podobne

B) Unhandled promise rejection / exception v intervale (scheduler)

Scheduler (reaper, cleanup, queue worker) keď vyhodí error bez catchu, Node to môže zložiť podľa nastavenia.

Musíš pridať globálne handlery (toto je “lacný alarm” ktorý ti hneď povie pravdu):

process.on("unhandledRejection", (reason) => {
  console.error("[FATAL] unhandledRejection", reason);
});
process.on("uncaughtException", (err) => {
  console.error("[FATAL] uncaughtException", err);
});

A potom obaliť všetky setInterval tick funkcie:

setInterval(() => {
  void (async () => {
    try {
      await doCleanup();
    } catch (e) {
      console.error("[CLEANUP] failed", e);
    }
  })();
}, 5 * 60 * 1000);
C) WebSocket / polling leak (listener narastá)

Ak pri každom requeste pridávaš listener (alebo WS subscription) a neodoberáš, časom padne.

Symptóm: “beží stabilne”, potom po čase zrazu padne.

Čo konkrétne by som spravil teraz (bez zbytočných otázok)

Nechaj React fix s EMPTY_* + uprav deps v najrizikovejších useEffect (tam kde robíš setSelectedManufacturerId, setBrandSearch, form.reset atď.)

Pridaj global fatal handlers do server entrypointu (1 min práce, obrovský prínos)

Oba schedulery (Photo reaper + queue worker) obaliť try/catch, logovať chyby

Ak používaš sharp/HEIC:

obmedz paralelizmus generovania variantov (p-limit)

zníž maxWidth v sanitize (napr. 2048)

Skontroluj, či /uploads nie je static (ak je, vypnúť)
