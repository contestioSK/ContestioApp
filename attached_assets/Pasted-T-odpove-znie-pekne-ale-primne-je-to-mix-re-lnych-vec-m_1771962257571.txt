Tá odpoveď znie pekne, ale úprimne: je to mix reálnych vecí + marketingového “všetko je v pohode”. Bez konkrétnych dôkazov z kódu to nie je audit, len checklist.

Tu je môj verdikt a čo by som na tom skontroloval ako prvé.

Čo je na tej odpovedi podozrivé / slabé
1) “Globálny middleware čistí všetky req.body polia (XSS ochrana)”

Toto je najväčší red flag.

Sanitizovať vstupy “odstraňovaním <script>” nie je robustná XSS ochrana.

XSS sa rieši hlavne escapingom pri renderovaní + zákaz dangerouslySetInnerHTML.

Takáto sanitizácia ti môže rozbiť legit texty a zároveň nezachytí XSS cez SVG, entity, CSS, URL payloady, alebo cez miesta mimo req.body (query params, headers).

👉 Ak sa spoliehate na “odstraňujem script tagy”, je to falošný pocit bezpečia.

2) HSTS “preload”

Preload nie je len “nastavím HSTS na 1 rok”.
Musíš mať:

includeSubDomains

preload
a hlavne: doména musí byť reálne v preload liste (inak to nie je preload).

👉 Toto sa dá ľahko tvrdiť, ale často to nie je pravda.

3) Rate limiting čísla sú divné

“Create catches: 150/min” – na rybársky denník je to absurdné. Reálne user nevytvorí 150 úlovkov za minútu. To je skôr pozvánka na abuse / bug loop.

“Authenticated 2000/15 min kvôli live polling” – pollovanie sa rieši lepšie (WebSocket/SSE), nie tým, že dáš obrovský limit.

👉 Toto nie je kritická diera, ale je to typické “uvolníme všetko, aby to fungovalo”.

4) “CSRF je ošetrené”

V texte to síce spomenul (“CSRF ošetrené”), ale neuviedol ako.

Pri cookie-based sessions je CSRF relevantné.

sameSite=lax pomáha, ale nie je to magické riešenie pre všetko (napr. niektoré POST scenáre, top-level navigácie, staršie prehliadače, alebo endpointy bez dodatočnej ochrany).

👉 Potrebujem vidieť: používate CSRF tokeny? alebo máte všetko strict cez sameSite + CORS + anti-CSRF hlavičky?

5) “CORS len konkrétne domény”

CORS nerieši útoky z browsera, keď používate cookies a útočník vie usera dostať na svoju stránku.
CORS chráni čítanie odpovedí, nie odoslanie requestu.

👉 Toto sa často zamieňa za CSRF ochranu.

Čo je naopak dobré (ak je to pravda v kóde)

Overený Stripe webhook cez constructEvent ✅ (ale treba pozrieť raw body handling)

ORM parametrizované query ✅ (SQLi nízke riziko)

Session v DB, httpOnly cookies ✅

CSP/Helmet ✅ (ale detaily sú dôležité)

Najväčšie reálne riziká, ktoré ten “audit” vôbec nepokrýva

Toto sú typické killer bugy v tvojom type appky:

A) Autorizácia / IDOR (najčastejšie)

Otázka: vie user:

upraviť cudzí catch/trip len zmenou id v URL?

vidieť cudzie battle dáta, výsledky, registrácie?

pridať fotky k cudziemu catchu cez /catches/:id/photos?

👉 Toto je kritickejšie než CSP. A v texte to nie je preukázané.

B) File upload bezpečnosť

HEIC je banalita. Reálne riziká:

limit veľkosti súboru + počet uploadov

MIME sniffing (tvári sa ako jpg, ale je to niečo iné)

SVG upload (ak povolené) = XSS

ukladanie názvov súborov (path traversal)

spracovanie obrázkov (ImageMagick/libvips) – historicky veľa CVE

C) Stripe webhook replay a idempotencia

Aj keď podpis sedí, treba riešiť:

idempotentné spracovanie eventov (Stripe posiela opakovane)

ochrana pred “double fulfill”

validácia event.type + livemode + expected account

D) “Token v URL” na PATCH registration

Toto môže byť OK, ale:

token musí byť kryptograficky silný (min 128 bit random)

musí mať expiráciu

musí byť single-use alebo viazaný na stav

logovanie URL môže token prezradiť (analytics, server logs, referer)

👉 Toto je dosť dôležité.

Čo by som urobil ako ďalší krok (prakticky, bez omáčok)

Ak chceš reálny audit, nie PR text, tak si vypýtaj od Replitu konkrétne dôkazy:

Zoznam všetkých endpointov a pre každý:

vyžaduje auth? (áno/nie)

ak áno: aká autorizácia? (owner check? role? battle participant?)

riziko IDOR: low/med/high

Pre file upload:

max size, max count, MIME validation, server-side re-encode (ideálne)

kde sa súbory ukladajú a ako sa servujú (separátna doména? correct headers?)

Pre sessions/cookies:

secure vždy true v prod?

sameSite a prečo

rotácia session id po login?

Pre Stripe:

raw body handling

idempotency store podľa event.id

kontrola event.livemode

Pre token v URL:

ako je generovaný (dĺžka, random zdroj)

expiruje?

je viazaný na konkrétny registration id?

logovanie/referrer mitigácie?

Moja známka tej odpovede

Ako “first pass checklist”: OK.
Ako “komplexný bezpečnostný audit”: nie.

Je to príliš všeobecné a najkritickejšie riziká (IDOR/autorizácia + token link + upload) sú len okrajovo.
